## 摘要

**ProxyScope 是一个自建的 HTTP/HTTPS 抓包代理服务。**

它在服务器上监听一个端口，让浏览器或命令行工具的流量主动经过它。经过的每一个请求与响应都会被完整抓取、解析并存入数据库，随后可以通过内建的 Web 界面按关键字、主机名、状态码等条件检索，查看完整的请求报文与响应报文。

定位上相当于 **Burp Suite 或 Yakit 里的「Proxy + HTTP History」两个模块**，但只专注做一件事：把流量抓下来、存起来、查得到。

目前已部署在腾讯云 VPS（`43.142.120.252`），以 systemd 服务形式常驻运行，开机自动拉起，仅监听本地回环地址，通过 SSH 隧道访问。

## 一、这个服务是做什么的

### 1.1 一句话理解

把它当作一个**带录像功能的网络中转站**：

```
原本：  你的程序 ──────────────────────► 目标网站
现在：  你的程序 ──► ProxyScope ──► 目标网站
                        │
                        └──► 誊写一份存档（可随时翻查）
```

流量原本直接发往目标网站，现在改为先送到 ProxyScope，由它转发；它在中转的同时把双方往来的全部内容记录一份存档，事后随时可以翻查。

### 1.2 核心能力

| 能力 | 说明 |
|---|---|
| **HTTP 抓取** | 完整记录请求行、请求头、请求体，以及状态行、响应头、响应体 |
| **HTTPS 解密** | 通过自签 CA 对 CONNECT 隧道做中间人解密，还原明文后入库 |
| **全文检索** | 基于 SQLite FTS5 建索引，可**直接搜索请求体/响应体正文**，而非只匹配 URL |
| **条件过滤** | 主机名模糊匹配、HTTP 方法、状态码（支持 `2xx` `4xx` `>=400`）、协议 |
| **报文查看** | 请求侧与响应侧各以完整 HTTP 报文形式呈现，头与体连贯展示 |
| **自动解压** | gzip / deflate / br / zstd 响应体入库前自动解码，避免乱码 |
| **异步高并发** | 单进程 asyncio，本地目标实测 115 req/s，单请求开销 8.7ms |
| **REST 接口** | 全部数据可通过 HTTP API 消费，便于脚本化与二次开发 |

### 1.3 与常见工具对比

| 对比项 | ProxyScope | Burp Suite | Yakit |
|---|---|---|---|
| 定位 | 纯抓包 + 检索 | 完整渗透测试平台 | 完整安全平台 |
| HTTPS 解密 | 支持 | 支持 | 支持 |
| 正文全文检索 | 支持（FTS5 索引） | 社区版受限 | 支持 |
| 运行依赖 | **仅 Python 标准库** | Java 运行时 | 独立客户端 |
| 部署形态 | **可常驻服务器，Web 访问** | 桌面应用 | 桌面应用为主 |
| 扩展能力 | 无插件体系 | 插件丰富 | 插件丰富 |

> **选型建议**：需要完整安全测试流水线 → 用 Burp / Yakit；
> 只需要一个轻量、可长期挂在服务器上、能随时查历史流量的抓包服务 → ProxyScope 更合适。

### 1.4 工作原理

| 步骤 | 发生的事 |
|---|---|
| **① 客户端改道** | 浏览器/工具配置代理后，请求不再直连目标，先发往 ProxyScope |
| **② 建立隧道** | 对 HTTPS 目标，客户端发 `CONNECT`；ProxyScope 回应 `200`，建立隧道 |
| **③ 中间人解密** | 用自签 CA 为该域名即时签发证书，与客户端完成 TLS 握手，获得明文 |
| **④ 转发并记录** | 明文请求转发给真实服务器，响应回传时同步写入 SQLite 与全文索引 |

第 ③ 步是 HTTPS 能被看到的关键，也是**为什么必须让系统信任根证书** —— 否则浏览器会发现证书并非真实站点签发，弹出安全警告。

### 1.5 适用场景与边界

**✅ 适用**

- 授权范围内的 Web 系统测试，观察接口参数与返回结构
- 排查某接口为何返回异常，需要查看完整请求头与响应体
- 长期挂机记录某系统流量，事后回溯检索（如查找是否曾泄露某类字段）
- 教学或研究环境，观察 HTTP/HTTPS 协议的实际交互

**⚠️ 不适用 / 需注意**

- 仅支持 **HTTP/1.1**，HTTP/2 会被降级为 1.1 处理，非原生支持
- WebSocket 升级后转为纯隧道转发，**只记录握手，不解析帧内容**
- 数据库明文存储，包含 Cookie / Token 等敏感信息，用完应清空
- **不得用于未获授权的系统与流量**

### 2.5 网络暴露策略（重要）

服务**刻意只监听 `127.0.0.1`**，未对公网开放任何端口。实测确认：

| 端口 | 外网可达性 |
|---|---|
| `22` (SSH) | ✅ 可达 |
| `18888` (代理) | ❌ 不可达 |
| `18787` (Web) | ❌ 不可达 |

**为什么这样设计**：Web 界面本身不带登录认证。若直接暴露到公网，任何知道地址的人都能查看抓到的全部内容，包括 Cookie 与令牌。通过 SSH 隧道访问，安全性等同于 SSH 本身，无需额外改造。

## 三、如何使用

### 3.1 第一步：建立 SSH 隧道

在你自己的电脑上执行（Windows / macOS / Linux 通用）：

```bash
ssh -L 18787:127.0.0.1:18787 -L 18888:127.0.0.1:18888 ubuntu@43.142.120.252
```

这条命令把服务器两个端口映射到本机同名端口。**保持该终端窗口开启**，隧道即生效；关闭窗口则隧道断开（服务器上的服务不受影响，仍在运行）。

### 3.2 第二步：让流量经过代理

**方式 A —— 只给浏览器或单个工具配置**（推荐，影响面最小）

代理地址填 `127.0.0.1:18888`，HTTP 与 HTTPS 共用同一端口。

**方式 B —— 命令行工具临时指定**

```bash
curl --proxy http://127.0.0.1:18888 \
     --cacert proxyscope-ca.crt \
     https://目标地址
```

### 3.3 第三步：信任根证书

要让 HTTPS 内容可读，必须让客户端信任 ProxyScope 的根证书。

**获取方式**：浏览器访问 <http://127.0.0.1:18787/api/ca.crt> 下载，或从服务器取 `/opt/proxyscope/data/certs/proxyscope-ca.crt`。

| 系统 | 信任方式 |
|---|---|
| **Windows** | 双击 `.crt` → 安装证书 → 当前用户 → 受信任的根证书颁发机构 |
| **macOS** | 双击导入「钥匙串访问」→ 设为「始终信任」 |
| **Linux** | `sudo cp proxyscope-ca.crt /usr/local/share/ca-certificates/` 后 `sudo update-ca-certificates` |
| **Firefox** | 独立证书库，需在 设置 → 证书 → 颁发机构 中单独导入 |

> ⚠️ 此证书仅用于本代理，安装后请勿用于其他用途；不再使用时建议移除。

### 3.4 第四步：查看与检索流量

浏览器打开 <http://127.0.0.1:18787> 进入界面。

**界面布局**

| 区域 | 功能 |
|---|---|
| 左侧列表 | 实时列出所有请求：序号、方法、状态码、时间、主机、路径、大小、耗时 |
| 顶部工具条 | 关键字全文检索、主机过滤、方法过滤、状态码过滤、协议过滤 |
| 右侧详情 | 三个标签页：**概要 / 请求 / 响应** |

**详情页结构**（按需求设计：头体合并）

- **「请求」页** — 请求行 + 请求头 + 请求体，合并为一段完整 HTTP 报文
- **「响应」页** — 状态行 + 响应头 + 响应体，合并为一段完整 HTTP 报文

JSON 正文自动格式化，图片直接内联预览，并提供「复制全文」按钮。

### 3.5 检索技巧

| 需求 | 操作 |
|---|---|
| 找某个密码/令牌出现在哪 | 搜索框直接输入该字符串，会命中请求体与响应体正文 |
| 只看某个站点 | host 过滤框填域名片段，支持模糊匹配 |
| 只看出错的请求 | 状态码选 `>=400` |
| 只看提交数据的请求 | 方法选 `POST` |
| 只看 HTTPS | 协议选「仅 HTTPS」 |

> 检索模式下自动刷新不会打断当前结果，便于一边观察一边筛选；「重置」按钮可清空全部条件。

## 五、运维手册

```bash
# 查看状态
sudo systemctl status proxyscope

# 重启服务
sudo systemctl restart proxyscope

# 停止服务
sudo systemctl stop proxyscope

# 实时日志
sudo journalctl -u proxyscope -f

# 最近 100 行日志
sudo journalctl -u proxyscope -n 100 --no-pager

# 清空抓包记录
curl -X POST http://127.0.0.1:18787/api/flows/clear

# 查看统计
curl http://127.0.0.1:18787/api/stats

# 健康检查
curl http://127.0.0.1:18787/api/health
```

### REST API 一览

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/flows` | GET | 列表；参数 `q` `host` `method` `status` `scheme` `mime` `since` `until` `limit` `offset` |
| `/api/flows/{id}` | GET | 单条详情，含 base64 编码的请求/响应体 |
| `/api/stats` | GET | 统计、代理状态、热点主机 |
| `/api/flows/delete` | POST | `{"ids":[1,2]}` 删除指定记录 |
| `/api/flows/clear` | POST | 清空全部记录 |
| `/api/ca.crt` | GET | 下载根证书 |
| `/api/health` | GET | 健康检查 |

## 七、已知限制与注意事项

1. **协议版本** — 仅支持 HTTP/1.1，HTTP/2 降级处理；WebSocket 仅记录握手
2. **数据敏感** — `flows.db` 明文存储，含 Cookie 与令牌，测试结束应清空或删除
3. **容量控制** — 默认最多保留 20 万条，超出自动清理最旧记录；单条正文超 2 MB 会截断
4. **证书安全** — `data/certs` 下的私钥泄露等同于可伪造任意站点证书，切勿外传
5. **合规要求** — 仅可用于自身拥有或已获书面授权的系统与流量

## 附：本次部署中修复的关键缺陷

供后续维护参考。这些问题在部署过程中真实暴露并已修复：

| 问题 | 根因 | 影响 |
|---|---|---|
| HTTPS 在服务器上完全抓不到 | `StreamWriter.start_tls()` 是 Python **3.11** 才有的 API，3.10 上调用直接 `AttributeError` | CONNECT 隧道建成后 TLS 握手即断，客户端看到 `unexpected eof`。**已改为 `loop.start_tls()` 兜底，跨 3.8~3.13 可用** |
| Windows 启动脚本中文乱码 | `.bat` 是 UTF-8，但 cmd 按 ANSI(936) 解析 | 提示文字全部乱码。**已改为纯 ASCII，中文交由 Python 输出** |
| Python 输出中文仍乱码 | `chcp 65001` + `PYTHONIOENCODING` 不足以让 Python 输出 UTF-8 | **补 `PYTHONUTF8=1`**，退出时恢复原代码页 |
| `where python` 选中商店空壳 | 命中了 `WindowsApps\python.exe` 存根 | 启动失败。**已优先 `py` 启动器并跳过 WindowsApps** |
| Web 服务刷 `ConnectionResetError` | 浏览器预连接被关闭 | 日志噪音。**已在 `handle_error` 中静默** |

> 其中第一条是**只有部署到真实 3.10 服务器才会暴露**的问题 —— 在 Python 3.11/3.12 的开发机上永远复现不出来。
